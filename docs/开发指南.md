# 开发指南

## 环境与安装

开发环境使用 Node.js 22 或更新版本；`package.json` 的 `engines.node` 是本地最低要求。持续集成同时在 Node.js 22 和 24 上执行构建与测试。

```sh
npm ci
```

`npm ci` 按 `package-lock.json` 安装依赖，不修改锁文件。源码入口为 `src/main.ts`；脚本位于 `scripts/`，单元与浏览器测试分别位于 `tests/unit/`、`tests/browser/`，共用入口和 Obsidian 模拟层位于 `tests/support/`，固定输入位于 `tests/fixtures/`。

## 常用命令

| 命令 | 用途 |
| --- | --- |
| `npm run dev` | 生成 `styles.css`，同时监听 TypeScript 与 `src/styles/`，生成带内联 source map 的 `main.js` |
| `npm run build` | 执行 TypeScript 检查，生成根目录 `styles.css`，并打包压缩的生产 `main.js` |
| `npm run build:styles` | 按固定顺序合并 `src/styles/*.css`，生成根目录 `styles.css` |
| `npm run check:styles` | 检查根目录 `styles.css` 是否与有序样式源一致，不改写文件 |
| `npm run check:docs` | 检查文档相对链接、示例路径和已删除截图引用 |
| `npm run typecheck` | 只执行 TypeScript 类型检查 |
| `npm run lint` | 运行 ESLint |
| `npm test` | 运行 `tests/unit/run.mjs` 中的解析、同步、兼容与交互回归测试 |
| `npm run test:browser` | 运行 `tests/browser/run.mjs`，使用本机 Chrome／Edge 或 `CHROME_PATH` 指定的浏览器检查布局和交互 |

浏览器测试使用 `tests/support/` 的合成 Vault 与 Obsidian API 模拟层以及 `tests/fixtures/dashboard.md`，不能替代真实 Obsidian 客户端验收。影响界面、Vault 写入或兼容逻辑时，除自动测试外还应在独立测试 Vault 中核对。

## 样式生成

样式源位于 `src/styles/`，文件名前缀与固定层级对应；实际合并顺序和生成逻辑以 `scripts/styles.mjs` 中的唯一清单为准。根目录 `styles.css` 是受版本控制的发布产物，文件头带生成提示，不应直接编辑。

开发服务器启动时会先生成一次样式，并同时监听 TypeScript 和 CSS 源。提交前应执行 `npm run build` 与 `npm run check:styles`，确认源码和根产物一致。

## 发布产物

插件发布产物位于仓库根目录：

- `main.js`：由 esbuild 从 `src/main.ts` 打包生成；
- `styles.css`：由 `src/styles/` 生成的插件样式；
- `manifest.json`：插件 ID、显示名称、版本和最低 Obsidian 版本。

安装时将这三个文件复制到 `<Vault>/.obsidian/plugins/reman-workspace/`。`versions.json` 是插件版本到最低 Obsidian 版本的兼容映射，不属于运行时复制的三个文件，但属于发布元数据。

## 版本更新

`package.json` 的 `version` 生命周期脚本调用 `scripts/version-bump.mjs`。脚本读取 `npm_package_version`，将其写入 `manifest.json`，并按 `manifest.json` 的 `minAppVersion` 更新 `versions.json`，随后暂存这两个文件。

当前脚本只有在该最低 Obsidian 版本尚未出现在 `versions.json` 的映射值中时才新增条目；如果发布要求每个插件版本都有独立键，打标签前应人工核对 `versions.json`。

推荐发布前执行：

```sh
npm version patch
npm run build
npm run check:styles
npm run check:docs
npm run lint
npm test
npm run test:browser
```

也可根据变更选择 `minor` 或 `major`。提交或标签创建前，确认 `package.json`、`package-lock.json`、`manifest.json` 与 `versions.json` 的版本关系符合预期，并检查根目录三个发布产物。

## 持续集成与标签发布

`.github/workflows/lint.yml` 在分支推送和拉取请求上使用 Node.js 22、24 执行 `npm ci`、构建、样式一致性检查、文档检查、`main.js`／`styles.css` 生成物差异检查、lint 和 `npm test`。当前 CI 不运行 `npm run test:browser`，真实浏览器测试仍是本地最终验收。

`.github/workflows/release.yml` 监听任意 Git tag。标签推送后，工作流在 Node.js 22 上重新安装依赖并构建，为 `main.js`、`manifest.json`、`styles.css` 生成构建来源证明，然后创建 GitHub Release、附加这三个文件并生成发布说明。

```sh
git push origin <branch> --follow-tags
```

推送标签前应先让普通 CI 通过，并确认标签版本与包和清单版本一致。

## 变更检查

涉及主页数据或迁移兼容时，至少检查以下契约：

- `parse(serialize(data))` 不丢失当前支持的数据；
- 旧天气块保持原始 Markdown，旧 `notes` 分区可归一读取；
- `DashboardUpdate` 的范围覆盖真实 UI 影响；
- Todo 来源卡写入仍只修改来源任务的复选框字符，不进入主页同步链路；
- 新弹窗或其他门户节点正确继承工作台主题变量。
